## 2. 产品目标与固定决定

让当前游客可以升级为有邮箱归属、可以重新登录的正式账号，保留已有比赛权限；让正式账号在其他浏览器登录后访问同一环境内的战绩，并通过邮箱找回密码。

| 项目 | V3 决定 |
| --- | --- |
| 游客 | 继续允许游客创建房间、对战与使用既有功能，不强制注册 |
| 登录标识 | 邮箱；昵称仅展示，不作登录凭据 |
| 日常登录 | 邮箱＋密码，不要求每次登录都收验证码 |
| 注册验证 | 六位数字邮箱验证码，十分钟有效，六十秒后可重发 |
| 新账号归属 | 已验证邮箱绑定当前游客原 userId，不重新分配历史归属 |
| 已有账号登录 | 使用账号自身 userId，不自动合并当前游客记录 |
| 密码找回 | 验证邮箱控制权后设置新密码，成功后重新登录 |
| 修改密码 | 已登录正式账号验证当前密码后设置新密码 |
| 会话 | 服务器端可撤销会话；登录有效期先沿用三十天 |
| 多端 | 允许同一账号多个登录会话，但同一玩家同时只有一个麻将控制连接 |
| 历史保存 | 沿用已有数据保存策略，注册不自动延长为永久牌谱保存 |
| 发布 | 先验证独立预览环境，后实施正式环境迁移和发布 |

昵称可以重名，首版账号功能不提供昵称修改、头像上传或用户主页。角色名、比赛开场昵称快照不因以后账号信息变化重写。

### 2.1 邮箱与密码格式

邮箱首期接受常见 ASCII 邮箱地址。去除地址首尾空白，保留实际投递地址；账号比较键统一转为小写，作为本产品的大小写不敏感登录规则。不删除 Gmail 地址中的点、不去掉加号后缀，也不按邮箱供应商猜测两个地址是否同属一人。

一个环境内一个 emailKey 最多绑定一个正式账号，一个 userId 最多绑定一个正式邮箱。邮箱变更、账号合并与多个登录邮箱不纳入本期。

密码长度先定为 12～128 个 Unicode 字符，允许密码管理器粘贴；不强制大小写、数字、符号的组合规则。密码按原值处理，不自动 trim、不截断；重设或修改时要求再次输入确认。

## 4. 页面与用户流程

### 4.1 首页与个人页

游客显示“游客身份，注册后可在其他浏览器登录”，提供“注册账号”“登录已有账号”。正式账号显示昵称与脱敏邮箱，提供修改密码、退出登录。

注册、登录、找回密码均可回到原页面或邀请码入房流程。未经验证的输入不创建正式账号，不把昵称或未验证邮箱当作身份凭据。

### 4.2 注册新账号

1. 用户在当前游客会话中输入邮箱，点击发送验证码。
2. 服务器创建 REGISTER 挑战，校验频率与预算，提交发送任务；页面显示统一的请求受理提示和重发倒计时。
3. 用户在原注册页面输入六位验证码，服务器核对用途、环境、邮箱、发起会话和有效期。
4. 验证成功后，签发五分钟有效、仅限本次注册的单次完成凭据；页面进入设置密码与确认密码。
5. 提交完成凭据与密码，事务内复核邮箱唯一性、游客尚未绑定账号及凭据未被消费，创建正式账号资料并保留原 userId。
6. 轮换登录会话令牌，旧游客令牌失效，重新绑定实时连接，页面显示注册成功。

验证码验证成功本身不直接把邮箱绑定给一个预先设置密码的账号。正式绑定与密码设置必须在持有原注册会话和完成凭据的同一流程中完成。

已注册邮箱也可收到用于证明邮箱控制权的注册用途验证码；只有验证成功后才明确提示“该邮箱已有账号，请登录或找回密码”。不创建第二个账号、不把当前游客并入那个账号、不替已有账号重设密码。

若两次注册并发争用同一邮箱，数据库唯一约束保证最多一次绑定成功。另一次明确进入已有账号处理，不迁移或覆盖任何历史。

### 4.3 日常登录

用户输入邮箱与密码，服务器核对正式账号，成功后签发新的登录会话。失败统一显示“邮箱或密码不正确”，不向未验证请求者区分邮箱是否存在。

在新浏览器登录同一账号时，得到原账号 userId 的历史、统计与回放权限。登录不能创建新的历史归属，也不能借昵称读取其他记录。

如果当前浏览器是另一个游客，登录前提示：本次切换不会合并当前游客记录；提供取消并先升级该游客的入口。退出后不承诺找回已丢失会话的游客身份，不能因为数据库里还有记录就允许按昵称找回。

如果当前浏览器已是另一正式账号，必须先明确退出，再登录；不提供无提示覆盖身份。相同账号的不同会话不自动抢占麻将控制权，仍走现有显式接管流程。

### 4.4 退出登录

退出撤销当前会话，清理该浏览器个人状态、暗手缓存和实时订阅。返回未登录首页；只有用户再次选择游客试玩时才创建新的游客，不悄悄把旧正式账号降级为游客。

退出当前设备不退出其他设备。账号本体、历史与成绩不删除，后续用邮箱密码重新登录可继续读取仍在保存期内的数据。

注册升级、普通退出或切换为不同 userId 不在牌桌中直接执行。当前浏览器正在控制未结束的比赛时，先明确转托管并退出该控制上下文，再进行身份操作；不得绕过点数损失、删除座位或暂停其他人。

服务端须校验原控制已释放，不能只靠前端隐藏按钮。仅关闭页面、不调用退出，仍按原掉线与会话过期规则处理。

### 4.5 忘记密码

1. 输入邮箱，申请 RESET_PASSWORD 用途验证码。
2. 无论邮箱是否存在，使用相同响应模板：“若该邮箱已注册，将收到验证码”；不向不存在的邮箱实际发送找回邮件。
3. 输入验证码；成功后获得仅限重设密码、五分钟有效、单次使用的完成凭据。
4. 输入新密码与确认，事务内消费凭据、更新密码并递增账号认证版本。
5. 撤销该账号全部旧会话和控制连接；显示“密码已重设，请重新登录”。

找回流程可以在另一个设备发起，不因原账号仍在比赛中而拒绝。被撤销的对局控制按窗口边界和托管规则处理，座位、点数和此前已收录选择保持。

验证码只是短期身份凭证，不能用于普通麻将请求、查看牌谱或其他用途。重设完成后不自动登录，不把找回页面所在的游客数据合并进被找回账号。

### 4.6 修改密码

已登录正式账号输入当前密码、新密码与确认。校验成功后，事务内更新密码、认证版本并撤销所有旧会话；只为当前操作重新签发一个新会话，其他设备需要重新登录。

当前密码错误、限流或数据库失败均不改变原密码。正在实际控制牌局时按第 4.4 节先处理托管；修改密码不额外要求发邮件。

## 5. 身份、历史与权限

### 5.1 数据保留原则

注册新账号采用原 userId 升级。以下数据不重写、不重新算分：比赛成员快照、最终点数、名次、牌谱、历史摘要、统计归属和回放观看位置。

账号升级成功前是游客；成功后是正式账号。事务失败不得出现“邮箱已经被占用，但玩家仍无法登录”的半完成状态。旧 userId 不得先删除再用新 userId 补数据。

登录已有账号只切换会话所属身份，不自动修改任何比赛的参与者。账号注册不能扩大房间历史读取权限，新加入房间的账号仍不能读取自己未参加的旧牌谱。

### 5.2 游客过期与不可恢复数据

当前有效游客会话可以升级；已经丢失、过期或清除的游客会话不能仅凭新提供的邮箱或昵称认领旧记录。

账号登录能力与比赛保存期限是两件事。正式账号不会随一次登录会话到期而消失，但完整牌谱和成绩继续遵守已公布的保存策略；注册不自动承诺永久保存。

### 5.3 会话与实时连接

正式账号资料与登录会话分离保存；一个账号可有多份会话，邮箱和密码哈希不复制到每份会话或游戏快照。

会话 Cookie 使用 HttpOnly、Secure、合适的 SameSite 和环境专属名称／路径。登录、注册升级和改密轮换令牌；数据库只保存可验证的令牌摘要，不保存原始会话令牌。

HTTP 请求与 Socket.IO 动作必须检查服务端会话、过期时间和账号认证版本。不能只在握手时认证，然后让已退出或已重设密码的旧连接继续执行操作。

找回／改密与出牌并发时，以串行提交边界决定先后：撤销前已提交的合法动作保留；撤销生效后未提交的动作拒绝。同一个用户的多设备仍只有一个有效麻将控制 binding，不因新账号体系生成重复座位。

## 6. 验证码、凭据与限流

### 6.1 验证码规则

| 项目 | 固定决定 |
| --- | --- |
| 字符 | 均匀随机的六位数字，允许前导零 |
| 有效期 | 挑战创建并提交后十分钟；排队与重试不延长 |
| 用途 | REGISTER 与 RESET_PASSWORD 完全隔离 |
| 绑定 | 环境、用途、规范化邮箱和发起流程；注册另绑定有效游客会话 |
| 单次使用 | 验证成功原子消费验证码，再签发受限完成凭据 |
| 重发间隔 | 同一邮箱至少六十秒；由服务器判断，不依赖浏览器倒计时 |
| 重发效果 | 同一邮箱、同用途的旧验证码立即失效，只认最新挑战 |
| 单挑战失败上限 | 五次；达到后该挑战作废，不能继续猜测 |
| 完成凭据 | 随机高熵，五分钟有效，单次使用，只能完成对应注册／重设 |

验证码使用安全随机源。数据库保存带独立服务端密钥的 HMAC 验证值，并纳入 challengeId、邮箱、用途与环境；不只对六位码做普通散列。

完成凭据保存在受限流程中，服务端只存摘要；不放进 URL、日志或诊断导出。验证码成功后，注册完成凭据也只能被原注册会话使用；换个浏览器输入同一个已消费码不会自动绑定身份。

验证码重发后若邮件发送失败，旧码仍保持作废，页面提示稍后重新申请；不把失效旧码重新激活。多个标签页同时申请时按服务器顺序决定最新挑战。

### 6.2 初始限流参数

以下为初始产品参数，可由受限服务配置调整；调整须记录，不在前端任意覆盖。

| 维度 | 初始限制 |
| --- | --- |
| 同一邮箱发码 | 各用途合计每小时五次、每天二十次，且满足六十秒冷却 |
| 同一来源 IP 发码 | 每小时二十次、每天一百次 |
| 全站实际 SMTP 尝试 | 默认每天一百次，包含重试；开通更高业务预算后显式调整 |
| 同邮箱／用途验证失败 | 十五分钟内十次；重发不会清空该累计计数 |
| 密码登录失败 | 账号比较键与来源 IP 分别统计；初始阈值每十五分钟十次，触发短期退避 |

限流与验证码消费须在服务重启后仍然有效，跨标签或并发请求不能绕过。阈值比较不能让陌生人通过连续失败永久锁死另一个账号。

找回密码的匿名响应与发送结果查询不能泄漏邮箱是否注册，包括不存在邮箱时的流程差异。内部可记录真实发送失败，玩家提示使用不暴露账号存在性的统一文案。

## 7. 密码存储与身份操作要求

密码使用 Argon2id 保存，独立随机盐；编码结果包含参数，便于以后升级。参数实施时依据官方安全基线和当前服务器负载校准，并记录在验收报告中。验证不能使用可逆加密、明文或普通 SHA 哈希代替专用密码哈希。

哈希任务采用有并发上限的异步执行，避免登录请求阻塞麻将计时与裁决。账号枚举、错误密码和不存在账号使用统一提示，不返回内部用户状态。

所有身份变更接口使用 HTTPS、来源／CSRF 校验、运行时输入校验和业务幂等。密码、验证码、SMTP 密码、会话令牌不进入访问日志、错误栈、回放或诊断剪贴板。

本节参考[OWASP 密码存储建议](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)及[密码找回建议](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)，参数和流程以本文明确选择为准。

## 8. 邮件发送与故障行为

### 8.1 邮件内容

注册与找回分别使用独立主题和正文，包含：产品名、用途、六位验证码、十分钟有效期，以及“非本人操作可忽略”的说明。

预览邮件主题必须带“预览环境”，正文明确用于预览页面。正式邮件不携带预览地址，预览验证码不能用于正式环境。正文同时提供简洁纯文本和 HTML 内容，不包含用户密码、完整对局信息或营销内容。

收件人由当前身份流程决定，不能把测试 QQ 邮箱写成所有用户邮件的固定收件人。发件地址、显示名和应用链接由受限配置确定，不接受任意请求参数覆盖。

### 8.2 异步与重试

验证码挑战、幂等回执和发信任务在同一事务中提交，发信由独立任务执行；不在麻将串行裁决队列中等待 SMTP 网络。

任务至少区分 QUEUED、SENDING、ACCEPTED、FAILED、EXPIRED。ACCEPTED 只表示 SMTP 服务器接受，不标为“收件人已收到”。页面的验证码输入仍以真实收件和校验为准。

临时网络故障允许退避重试，最多额外两次，始终发送同一个挑战与同一个码；超过有效期不再发。认证错误、配置错误和永久拒信不无限重试。

SMTP 在服务器接受后断线时可能无法确认结果，不能声称邮件投递严格一次。任何必要重试仍受发送预算限制，不能因此创建多个有效验证码或多个账号。

队列为重试暂存的邮件正文须加密，密钥独立受限保管；完成、最终失败或过期后删除不再需要的验证码正文密文。长期日志只保留任务 ID、环境、用途、脱敏收件人、状态和必要错误类别。

### 8.3 不可用时

SMTP 未配置、认证失败或发信预算耗尽时，注册和找回流程明确不可用或提示稍后重试，不创建未经验证的账号、不向前端回显验证码。

邮件故障不能阻塞进行中的对局、既有游客功能或已有账号的密码登录。页面可根据服务能力开关禁用依赖邮件的入口，不能显示永远无法完成的注册表单。

## 9. 预览与正式环境

本项目现有正式与预览数据库、游客 Cookie 分离，V3 继续保持：

- 正式站为 mahjong.yangjm.cn，预览入口为该站 /preview/。
- 账号唯一性、验证码、完成凭据、登录会话和历史归属各自独立；同一邮箱可在两个环境分别注册。
- 本期不在正式与预览间自动迁移账号、密码、游客历史或比赛记录。
- 预览先启用收件白名单，仅允许用户已确认的测试邮箱；未在白名单的地址不执行真实 SMTP 发送。
- 同一发信地址可以服务两个环境，但邮件主题、应用来源、用途、队列和验证码密钥必须区分；发信预算同时考虑服务商账号总额度。
- 预览中的“注册成功”不能宣传为正式站账号已创建；正式站发布后需在其自身环境注册。

预览收件白名单是测试阶段限制，不是正式业务的固定收件地址。正式开放后，在限流和预算范围内向真实注册者填写的邮箱发信。

### 10.2 接口范围

以下沿用现有 /api/v2，新增认证能力，不因产品叫 V3 就把麻将实时协议强行改成 3.0。正式接口字段与错误码在编码前与 Schema 一起冻结。

| 方法与路径 | 用途 |
| --- | --- |
| GET /api/v2/capabilities | 扩展账号注册、邮件可用性和预览限制的安全能力字段 |
| GET /api/v2/me | 保留原 userId、房间／比赛字段，增加身份类型与本人脱敏邮箱 |
| POST /api/v2/auth/register/code | 当前游客申请注册验证码 |
| POST /api/v2/auth/register/verify | 校验 REGISTER 码，返回单次注册完成凭据 |
| POST /api/v2/auth/register/complete | 完成密码设置，原 userId 升级账号并轮换会话 |
| POST /api/v2/auth/login | 邮箱密码登录，签发新会话 |
| POST /api/v2/auth/logout | 撤销当前会话与其实时控制 |
| POST /api/v2/auth/password-reset/code | 申请找回验证码，使用统一受理响应 |
| POST /api/v2/auth/password-reset/verify | 校验找回码，返回受限重设凭据 |
| POST /api/v2/auth/password-reset/complete | 消费凭据重设密码并撤销全部旧会话 |
| POST /api/v2/auth/password/change | 正式账号验证当前密码后改密 |

正式身份绑定权只在通过服务端验证后产生。不能通过客户端传入 userId、emailVerified=true 或改 Cookie 内的显示信息完成升级。

所有修改请求携带幂等键。相同键相同载荷不重复发信／建号／消费凭据；相同键改载荷报冲突。敏感载荷的去重只保存带服务端密钥的摘要与必要业务结果，不持久化明文密码或验证码。

回执不持久化原始 Set-Cookie 或登录令牌。登录成功但响应丢失时，可以重新验证密码并签发新会话；账号与身份变更仍须幂等，不要求把旧明文令牌从数据库取出重放。

验证码验证响应丢失时，在原有效发起上下文与同一幂等请求仍可证明的前提下，可重新签发替代完成凭据并撤销旧凭据；不得再次消费验证码、延长原验证授权期限或执行注册／重设。完成凭据已用于提交注册／重设后不再重签，返回已提交结果并引导正常登录或新的找回流程。

## 12. 迁移与发布顺序

1. **固定当前版本**：记录实际代码、数据库与部署版本，不用旧验收报告替代当前基线。
2. **验证迁移副本**：从现有游客会话、成员与历史构建规范用户资料，保留全部 userId；同一 ID 的历史昵称冲突列入处理规则，不修改已冻结比赛昵称。
3. **保持游客兼容**：迁移不能批量注销全部旧游客，也不自动为游客绑定邮箱；旧会话仍按原有效期工作。
4. **实施账号与邮件**：加入事务、验证码、哈希、队列、限流、撤销和页面；账号功能以受控开关启用。
5. **预览配置与发信验证**：用户填写 SMTP 密码，先连接／认证，再向已确认的测试邮箱发送明确标记的测试邮件，最后跑真实注册和找回流程。
6. **游戏回归**：验证新旧身份、各浏览器、控制接管、原战绩及回放不回归；故障 SMTP 不影响正常对局。
7. **正式部署评审**：备份、迁移与回滚演练通过后安排正式发布；本次文档生成不执行发布。

回滚不能让注册后保留原 userId 的正式账号被旧程序当作任意游客覆盖。账号功能关闭只停止新注册／找回入口，不能绕过已有账号认证。新账号已有写入后，优先使用可读取新结构的修复版本，禁止直接恢复旧快照丢弃新账号或新成绩。

正式与预览原本使用不同数据，发布不会自动把预览注册记录复制到正式库。若未来要迁移，另做身份归属与冲突规格。
