## 1. 本次任务与交付范围

用户下一步会让 Claude 美化页面。目标是在现有可运行项目上提升视觉质量、信息层级、布局一致性和不同屏幕下的可用性，保留已有业务能力和操作语义。

当前没有指定参考网站、配色或视觉稿，也没有确认只改某个页面。建议先浏览全站，提出简短的视觉方向，再直接开展可回看的本地修改。现有风格为米白底、深绿、金色点缀、少量宋体与麻将主题装饰，可以沿用并精修；这是建议，不是用户已确认的设计要求。

本次默认交付为**本地可运行的页面改动和验证说明**。上线、数据库迁移、规则调整、账号体系重做不属于页面美化任务。

可优先改善：

- 全局颜色、字体、间距、按钮、表单、卡片、提示和弹窗的一致性。
- 首页的视觉重点与游客／账号／开房／加入房间入口。
- 房间等待页的座位、房主权限、准备状态、邀请信息。
- 牌桌上玩家、牌河、宝牌、手牌、行动按钮、倒计时的阅读顺序。
- 账号、好友、战绩、统计、规则和回放页面的排版与状态反馈。
- 窄屏、手机横屏、紧凑牌桌、键盘焦点和减少动效模式。

## 2. 项目结构与页面入口

技术栈：React 19 + TypeScript + Vite；普通 CSS；Express + Socket.IO；本地 SQLite／生产 PostgreSQL。当前没有使用 React Router、Tailwind 或组件库；不必为美化引入一整套新框架。

### 页面切换方式

`main.tsx` 通过内部 `screen` 状态切换 `home / room / game / rules / replay / history / stats / settings / account / social`。账号内部还有 `profile / register / login / reset / change`。

- 多数页面没有独立 URL，不能假设访问 `/room` 或 `/settings` 就能进入对应页面。
- `?invite=邀请码` 是加入房间的入口，`?replay=比赛ID` 是回放入口；保留这两个入口。
- 刷新后的身份、房间和牌局恢复依赖现有 API 与 Socket，不要改成刷新就回到一个静态首页。
- 实际对局 UI 从 `main.tsx` 调用 `Game`；不要只美化一份脱离实际数据的演示牌桌。

## 3. 启动与预览

需要 Node.js **24.7+** 和 pnpm **11+**，以根目录 `package.json`、`pnpm-lock.yaml` 为准。

```sh
cd /Users/yangjm/Documents/Mahjong
pnpm install --frozen-lockfile
```

推荐用独立本地数据库做页面开发，避免操作原有 `data/mahjong.sqlite` 中的身份和对局。下面分两个终端运行：

```sh
# 终端 A：后端。显式清空 DATABASE_URL，使用单独的本地数据目录。
NODE_ENV=development DATABASE_URL= SQLITE_PATH=data/ui-preview/mahjong.sqlite SESSION_COOKIE_NAME=mj_ui_preview_session PUBLIC_ORIGIN=http://127.0.0.1:5173 pnpm dev
```

```sh
# 终端 B：前端热更新。
pnpm dev:ui
```

打开 `http://127.0.0.1:5173`。Vite 将 `/api` 和 `/socket.io` 转给后端。若端口被占用，先检查现有进程；不要直接停止不明服务。变更端口时同步调整代理和 `PUBLIC_ORIGIN`。

检查构建后的页面可执行：

```sh
pnpm build
# 先停止上面的开发后端，再用同一独立数据库启动。
NODE_ENV=development DATABASE_URL= SQLITE_PATH=data/ui-preview/mahjong.sqlite SESSION_COOKIE_NAME=mj_ui_preview_session PUBLIC_ORIGIN=http://127.0.0.1:3000 pnpm start
```

此时访问 `http://127.0.0.1:3000`；构建结果位于 `dist/`，不要手改构建产物。

本地不配置 SMTP 也可以游客试玩、建房、加入 AI 和开始比赛。注册／找回入口受服务能力控制，不能因为本地未配邮件而移除已有功能。验证受限页面时使用独立测试配置或已有测试夹具，不为美化读取或复制真实邮件凭据。

## 4. 必须保留的功能约束

### 4.1 牌桌动作通道

以下两个文件实现了 V4.2 的关键行为，页面美化应尽量保持其逻辑不变：

- `frontend/src/table-actions.ts`：合法候选、当前决策标识、同步提交锁、自动动作调度、请求恢复。
- `frontend/src/use-table-actions.ts`：指针手势、键盘、焦点、前后台与连接生命周期、身份隔离偏好。

所有手动与自动操作必须继续通过现有控制器提交；不要给新按钮单独增加一条直接发送 Socket 动作的通道。`main.tsx` 中的身份、binding、最新 frame 二次授权检查也要保留。

| 当前交互 | 美化后必须保留 |
| --- | --- |
| 普通出牌 | 默认先选牌，再明确点击“打出” |
| 快速出牌 | 默认关闭；开启后完整单击／轻触普通弃牌才可直接提交，拖动、跨牌、滚动等不能误出牌 |
| 立直 | 即使开启快速出牌，也必须选择弃牌后明确确认 |
| 自动摸切 | 默认关闭；现有 500 毫秒等待、特殊选择暂停、手动介入及失焦停用规则不变 |
| 不鸣牌 | 默认关闭；不吃、不碰、不明杠，仍保留荣和提示；不影响本人暗杠／加杠选择 |
| 放弃荣和 | 保留确认弹窗，默认焦点在取消；取消弹窗不等于过牌 |
| 键盘 | 默认关闭且限定聚焦区域；方向键／Home／End 选牌、Enter 确认，R/C/P/K/W/Space/Esc 映射不变 |
| 动作提交后 | 保留锁与“等待裁决”反馈；不能因为动画结束、重绘或弹窗关闭就允许重复提交 |
| 回执未知 | 保留“查询／恢复原动作”“重新同步”等入口，沿用原 requestId 的恢复机制 |
| 断线／控制权变化 | 明确显示状态，沿用同步和接管流程；不能显示成仍可正常出牌 |

快速／键盘偏好按环境基础路径和用户身份隔离；自动模式不持久化。不要把四个开关统统存为全局永久偏好。

### 4.2 实体牌、隐藏信息与布局

- 牌是 **0–135 的实体 ID**，不是只有 34 种牌；`shared/types.ts` 中的 `kind`、`isRed`、`tileName` 是现有转换入口。
- 赤五实体为 `16 / 52 / 88`；选牌、React key 和动作候选继续按实体区分。不能按牌种合并同名手牌。
- 自己的摸牌 `drawnTile` 单独展示并有间隔／标记，保留最多 14 张牌时的完整可达性。
- 其他玩家暗手只显示牌背数量；不要为视觉效果在实际对局暴露其他玩家暗牌或牌山。
- 相对座位由 `viewerSeat` 计算，不能将东家永久当作当前玩家。
- 牌河需支持后期多行；保留立直横牌、摸切／手切、已被鸣走的牌和最近弃牌等表现。
- 副露、牌河、中央信息必须各有空间，不能用固定高度把后半局内容裁掉。
- 中央局况保留场风／局数、本场、供托、剩余牌数及宝牌指示牌。
- 和牌、流局、技术中止、最终排名、再来一局和回放入口要保留。

### 4.3 DOM 与可访问性契约

部分 DOM 属性不仅用于样式，也用于键盘、焦点、手势或浏览器验证。若改结构，先检查引用：

- 手牌的 `data-hand-tile` 用于选牌后滚动及浏览器定位；保留实体 ID。
- `controls.region`、`controls.dialog` 的 ref、`tabIndex`、键盘捕获事件和 `data-cancel` 关系不能丢。
- 动作弹窗的 `role="dialog"`、`aria-modal`、标题关联、Tab 焦点限制、关闭后焦点恢复，以及背景 `inert` 都要保留。
- 保留原生按钮的 `disabled`、牌的 `aria-label`／`aria-pressed`、复选框标签、`role="status"`／`alert` 和可见焦点。
- `.hand-panel`、`.own-hand`、`.action-modal` 等选择器在交互逻辑或验证中有引用；改名前先搜索全仓库。
- 选中牌与键盘焦点要能区分；不要只靠颜色传递关键状态。
- 不要为按钮／牌再添加一套全局快捷键或同时绑定多个出牌触发事件。

### 4.4 账号、好友与历史

- 游客注册当前身份后保留原 userId；登录已有账号不会自动合并游客记录。
- 正在控制牌局时，身份切换沿用现有明确转托管流程；退出后不会自动创建新游客。
- 账号／邮件／好友相关入口按服务能力展示，保留不可用、限流、加载、失败和空状态。
- 完整牌谱的访问受参与者身份和比赛正常结束状态限制；页面层不放宽授权。
- 自定义头像沿用现有上传、错误和回退逻辑；不能仅用 CSS 隐藏失败提示。

## 5. 样式与素材处理建议

`style.css` 同时包含早期牌桌规则、后来的 `.game-table.table-layout` 布局和 V4／V4.1／V4.2 增量样式。直接在文件末尾持续堆覆盖容易造成不同页面和屏幕表现不一致。

建议先整理颜色、字号、间距等公共变量，再按页面逐步修改。允许拆分样式或提取纯展示组件，但保留稳定的状态与动作边界；避免将一次美化扩大为全站状态管理重构。

现有关键适配包括 1000、720、600 等宽度附近的规则、竖屏、`max-height: 600px` 的横屏、`.table-compact` 和减少动效模式。改某个断点后检查其他规则是否继续覆盖它。

当前牌面为自绘 SVG／文字，桌面与首页插画主要由 CSS 绘制，头像为仓库内 SVG，字体使用系统字体。新增图片、图标或字体时确认使用许可并更新 `THIRD_PARTY_NOTICES.md`；优先随仓库交付，避免页面依赖外部 CDN 才能正常展示。

保留子路径部署兼容：API、Socket、头像和新增静态资源应沿用 `import.meta.env.BASE_URL` 等现有路径处理。不要把资源、请求或导航一律写死到站点根路径。

## 6. 验证与验收

### 自动检查

```sh
pnpm build
pnpm test:table
pnpm test
```

`test:table` 包含在完整测试中，修改牌桌时可先运行以获得较快反馈，交付前运行完整测试。不要为纯样式改动编写只检查 CSS 文本的测试；以现有行为回归和真实页面检查为主。

可用的浏览器验证：

```sh
pnpm test:table:browser
```

此脚本需环境中可导入的 Playwright 和可用浏览器，可通过 `PLAYWRIGHT_MODULE` 指向现有模块。它会覆盖写入部分 `reports/v42-*` 结果；保留原有历史证据的含义，交付时明确新一轮执行时间和结果。不要把“浏览器不可用”写成通过，也不要为运行此检查无必要地改生产依赖。

`scripts/verify-table-browser.ts` 使用真实 `Game` 和 hook 加确定性状态／传输夹具；`/__v42_fixture` 只由该脚本启动的测试服务注入，普通开发服务没有这个地址。夹具不能证明真实联网比赛全部通过。

牌桌后期布局的辅助检查：

```sh
node --import tsx scripts/render-table-layout.tsx
```

它生成 `data/table-layout/` 下的普通／紧凑、后期／压力布局 HTML，仅供检查 `TableSurface` 布局，不涉及真实数据库和对局，也不覆盖完整操作区。

子路径构建检查：

```sh
pnpm exec vite build --config frontend/vite.config.ts --base /preview/ --outDir /tmp/mahjong-ui-preview-dist
```

这只证明构建能完成。还需在 `/preview/` 挂载的实际预览中检查新增资源与入口，不能将构建通过等同于子路径功能验收。
