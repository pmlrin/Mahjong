## 1. 目标与范围决定

用户已确定 V4 优先完成“账号完善和好友系统”。本版目标是让正式账号具备稳定可辨认的个人资料，并能通过站内好友邀请快速组建已有的四人麻将房间。

本文件为上述方向固定首期实施选择：昵称修改、预设头像、登录设备管理、好友码、双向好友、在线状态、站内邀请、删除与屏蔽。无需接入新的邮件、短信、社交平台或文件存储服务。

### 1.1 当前基础与核对边界

当前源码版本为 `0.3.0`。按现有代码与 2026-11-01 上线记录，已有游客、邮箱注册／登录／找回／改密、可撤销会话、单一麻将控制连接、东风／半庄、双档 AI、同桌再战、战绩与牌谱。

本次核对的是本地源码、文档和既有报告，没有重新执行线上检查。V3 已有正式上线记录，不能沿用旧 V2 文档把“正式切换尚未执行”当作当前事实；真机、真实线路及精确故障竞争等未关闭事项仍独立跟踪。

## 3. 账号资料

### 3.1 个人页

正式账号个人页增加头像、昵称、只读脱敏邮箱、只读好友码与复制按钮，以及“编辑资料”“登录设备”“好友”入口。保留修改密码和退出当前登录。游客显示注册／登录引导，其原有游戏入口不受影响。

不向其他玩家公开邮箱、登录设备、创建账号时间或内部会话标识。好友码是社交查找标识，可以主动分享，但不能作为认证凭据。

### 3.2 昵称与头像规则

- 昵称提交时去掉首尾空白并进行 NFC 规范化，按 Unicode 码点限制为 1～16；不接受换行、控制字符和用于伪装文本方向的双向控制字符。
- 允许中文、常见文字、数字、空格和表情；允许重名，不凭昵称识别唯一账号。界面按纯文本显示，不解释为 HTML 或 Markdown。
- 既有昵称迁移时保留原值，不因新增校验导致用户无法登录；下一次主动修改时执行新规则。
- 头像提交固定 `avatarId`，服务器按白名单校验。12 款头像由固定 ID 与静态资源映射，统一默认头像；旧用户和旧记录缺省时使用默认头像。
- 每次资料更新提交 `expectedProfileVersion`；版本不匹配返回 `PROFILE_VERSION_CONFLICT`，要求刷新后重试，不静默覆盖另一设备修改。
- 昵称实际变化每 24 小时最多一次；仅更换头像不占改名次数，但资料写入仍限流。重放同一请求、不变更原值不重复消耗次数。

### 3.3 修改时机与冻结展示

为避免准备厅和已开场展示不一致，V4 仅允许未占据任何未结束房间位置时修改资料。处于 WAITING 或 PLAYING 时返回 `PROFILE_CHANGE_IN_ROOM`；用户自行返回房间处理，不自动离房、托管或取消准备。FINISHED／ABORTED 后若已进入新的再战等待厅，同样视为占位。

资料保存与开始比赛／入房必须在服务端按一致顺序校验，不能先检查无房间，随后与入房并发写入造成昵称来源不确定。

展示来源固定如下：

| 位置 | 昵称／头像来源 |
| --- | --- |
| 个人页、好友列表、待处理申请 | 当前账号资料，按版本刷新 |
| 新加入的等待厅 | 入房时冻结的资料；本版不支持在等待厅内改资料 |
| 新比赛的牌桌、结果、历史与牌谱 | 开场成员快照 |
| 已有比赛和旧牌谱 | 原记录昵称；缺失头像显示默认值，不回填当前头像 |

资料修改不更改 userId、好友关系、会话、比赛归属或观看位置，不重新签发密码会话。

## 4. 登录设备与会话管理

### 4.1 展示口径

“设备”表示一个有效登录会话，不是对物理设备的可靠识别。同一电脑的不同浏览器或重复登录可能出现多条。列表只包含本账号、本环境、未撤销且未到期的会话，每页最多 20 条，支持加载更多。

每项包含专用不透明 `sessionId`、是否当前会话、浏览器／系统大类、创建时间、到期时间及最近活动时间。最近活动最多每分钟持久化一次；历史会话没有活动资料时显示“暂无记录”，不能用迁移时间冒充登录时间。

不返回 token、tokenHash、Cookie、bindingId、完整 User-Agent、IP 地址或地理位置。设备名称是参考信息，不能作为安全证明。不做硬件指纹或额外定位。

### 4.2 退出其他设备

1. 用户选择某条其他会话，或“退出全部其他设备”。
2. 页面明确提示被退出设备会失去账号访问和出牌权限；若它正在控制牌局，将转为既有断控／托管流程。
3. 输入当前密码，服务器验证后在同一授权操作中撤销目标会话；V4 不另发设备管理邮件验证码。
4. 当前会话保持有效；全部其他设备操作按提交时刻有效会话集合执行，之后新建的登录会话不被追溯撤销。

本接口禁止撤销当前 `sessionId`，返回 `CURRENT_SESSION_NOT_ALLOWED`；当前设备退出沿用 V3 退出流程。密码错误／过期、目标属于其他账号均不产生撤销副作用。指定会话已撤销或过期时按幂等成功处理，但不泄露其他账号的会话是否存在。

远端会话撤销后，HTTP、Socket 消息入队执行和私有推送都必须重新校验有效性。若被撤销会话持有麻将控制权，沿用 V3 远端撤销：保留座位、点数及已提交选择，不延长窗口；未提交决策按既有截止和后续托管处理。当前设备不自动获得牌局控制，仍需显式接管。

撤销会话与在途麻将动作以权威提交顺序为准，已经成功提交的动作不能回退或再执行。推送清理失败可以重试，已撤销会话不能因此继续获取数据。重试同一幂等请求先验证当前会话，不能恢复目标会话。

## 5. 好友码与查找

> v4.4 起好友码停用，改为按注册先后从 100000 起发放的数字 UID，按 UID 精确查找；见 `docs/账号资料与好友接口-v4.0.md` 与 `docs/第四版配置与迁移-v4.0.md`。本节保留为 v4.0 的原始范围记录。

- 每个正式账号在本环境拥有唯一、稳定的 12 位随机好友码，使用 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` 字符集，通过安全随机源生成，数据库唯一约束冲突后重试。
- 展示可按 `XXXX-XXXX-XXXX` 分组；输入仅忽略首尾空白、分组连字符及 ASCII 大小写，不接受通配符。好友码不从 userId、邮箱、手机号或递增序号派生。
- 既有正式账号迁移时分配；游客升级账号时在原注册事务内分配，保留原 userId；游客没有好友码。
- 仅支持完整好友码精确查找。无昵称搜索、邮箱搜索、模糊匹配、推荐列表或公共目录；首期不支持重置好友码。
- 查找成功仅返回好友码、当前昵称／头像及调用者与该账号的关系状态。不返回邮箱、内部 userId、在线状态、房间、战绩或好友数量。
- 自己的好友码显示“这是你的账号”，不能发送申请；不存在或双方任一方屏蔽时统一返回“未找到可添加的账号”，不揭示屏蔽原因。

好友码和六位房间邀请码是两种独立标识，页面文案、输入框和校验必须区分。好友码不直接授予入房、观战、读取战绩或接管权限。

## 6. 好友申请与关系

### 6.1 生命周期

申请具有 `requestId`、发起人、接收人、创建时间、截止时间、版本与状态。产品申请 ID 与 HTTP 幂等键含义不同。状态为 `PENDING → ACCEPTED / REJECTED / CANCELED / EXPIRED / INVALIDATED`，终态不能重新打开。

1. 用户精确查找好友码，核对昵称／头像后点击申请；本版不提供自定义附言。
2. 接收人在“收到的申请”中同意或拒绝；发起人在“发出的申请”中可以撤回。
3. 同意时在事务内复查双方仍为正式账号、无屏蔽、申请未过期、好友上限及双方关系，创建一条双向好友关系并将申请终结。
4. 到期后显示已过期，不自动成为好友；所有到期判断均以服务器时间为准，客户端倒计时仅展示。

同一账号对之间最多一条待处理申请，使用规范化账号对和唯一约束保证。双方同时申请不自动互加：第二次返回现有申请，页面引导接收方明确同意。重复发送同方向申请不新增通知、不延长截止、不重复扣发送额度。已经是好友时返回已有关系。

申请有效期 7 天；每账号最多 200 位好友、50 条收到的待处理申请和 50 条发出的待处理申请。接受时任一方已满，返回 `FRIEND_LIMIT_REACHED`，原申请仍待处理直到到期。拒绝或撤回后，原发起人在同一账号对 24 小时内不能重新申请；双方主动删除好友后，双方均需等待 24 小时才能重新申请。

接受、拒绝、撤回、屏蔽和到期相互竞争时，仅一个合法事务结果生效。重复同一终结操作返回原结果；与已终结状态冲突的操作返回 `REQUEST_STATE_CONFLICT`。未知或无权访问的申请统一 404。

### 6.2 删除与屏蔽

删除好友需确认，删除的是双向关系；对方列表同步移除。不发送“被某人删除”的专门弹窗。删除同时使双方所有待处理入房邀请失效，但不踢出已经共同加入的房间，也不改变已有比赛权限。

屏蔽为单向持久设置，提供“已屏蔽账号”列表与解除入口。屏蔽时原子删除双向好友关系、使双方待处理申请和邀请失效、停止双方在线状态订阅。屏蔽者仍可在自己的列表中识别所屏蔽账号；被屏蔽者无法通过好友查找、申请或邀请识别屏蔽原因。

解除屏蔽不恢复好友、不恢复旧申请／邀请；解除后双方重新申请仍需满足无其他屏蔽与 24 小时冷却。每人最多屏蔽 500 个账号，达到上限时提示管理现有列表。

屏蔽只管理站内社交，不是同桌禁止功能。双方仍可能通过已有房间邀请码同桌，进行中的牌局不受影响；页面应清楚说明这一点。

## 7. 好友列表与在线状态

好友列表显示当前昵称、头像、好友码及以下状态：

| 状态 | 定义 |
| --- | --- |
| 离线 | 没有有效会话对应的活跃站内连接 |
| 在线 | 有活跃连接，未处于等待厅或运行中比赛 |
| 等待开局 | 有活跃连接，且已占据 WAITING 房间位置 |
| 对局中 | 有活跃连接，且占据 RUNNING 比赛座位，包括在线但正在托管的账号 |

有未结束比赛但没有活跃连接仍显示离线，不能把托管 AI 活动当作本人在线。任一有效会话的连接都可维持在线，不要求它取得麻将控制权。已结束比赛在未进入新等待厅时按在线处理。

通过现有连接心跳判断活跃；最后一个连接断开后保留至多 30 秒缓冲，未恢复则离线，已撤销会话不进入缓冲。正常可用网络中，显式房间状态变更在 5 秒内反映到好友端；在线状态用于展示，不保证可立即入房。

首期不支持隐身、忙碌开关、离线时间、精确最后上线时间。好友状态不包含 roomId、邀请码、对手、赛制、点数或手牌。排序为等待开局、在线、对局中、离线，同组按规范化昵称和稳定好友码排序；列表内可按已加载好友昵称筛选，不触发全站搜索。

非好友不能订阅状态。断线、删除、屏蔽、退出或会话失效后必须清除不再有权显示的状态；重新连接先重建权威好友快照，不能长期展示旧缓存。

## 8. 站内好友邀请

### 8.1 发出邀请

仅 WAITING 房间的当前房主可以邀请，且房间须至少有一个真实空槽；AI 占位不算空槽，必须由房主先按既有操作移除。发送者与接收者必须仍为无屏蔽的双向好友；接收者可以离线，下次上线在有效期内读取邀请。

邀请记录 `invitationId`、双方账号、roomId、lobbyGeneration、创建／截止时间、版本及状态，有效期 5 分钟。同一发送者、接收者、房间和准备轮次只保留一个待处理邀请；重发不延长有效期或增加通知。

发邀请不占座、不自动增删 AI、不自动准备，也不透露房间邀请码。卡片显示邀请人当前昵称／头像、东风或半庄、房间当前人数、截止时间及“接受／拒绝”；人数只是查询时的提示。

### 8.2 接受邀请

接收者主动接受时，服务器在既有房间串行裁决与数据库事务中重新校验：

1. 当前登录账号是指定接收者；邀请仍待处理且 `now < expiresAt`。
2. 双方仍为好友、无任一方向屏蔽；发送者仍是该房间房主和成员。
3. 房间仍为 WAITING，lobbyGeneration 与邀请一致；接收者尚未在目标准备厅时必须存在空槽。
4. 接收者没有另一个未结束房间／比赛；若已在目标准备厅，视为已加入，不重复占位、不再次清除准备，即使房间已满也不因此拒绝。
5. 校验后添加成员、清除既有真人准备、更新房间版本并将邀请置为 `JOINED`，在同一事务提交；之后才发布房间和社交通知。

成功后进入等待厅，不自动开场。加入后仍遵守原准备／开始规则。接受邀请仅加入房间，不自动接管该账号另一个浏览器的麻将控制连接；需要时仍显示原显式接管流程。

接收者在其他房间时返回 `ALREADY_IN_ROOM`，不自动离房或托管；邀请仍保持待处理，可在有效期内自行处理原房间后重试。不能提供跳过验证的“强制加入”。

### 8.3 失效、重复与竞争

邀请状态为 `PENDING → JOINED / DECLINED / CANCELED / EXPIRED / INVALIDATED`。接收者可拒绝，发送者可取消；对应版本与权限均在服务端核验。

- 房间开始、关闭、准备轮次变化、房主转移、发送者离开、删除好友或屏蔽，使该邀请失效。不能靠旧邀请加入下一轮再战等待厅。
- 接受时房满返回 `ROOM_FULL` 并使该邀请失效；后续有空位需房主重新邀请。不得移除 AI 或其他成员腾位。
- 多人争最后一席，仅一人加入；同一用户多端接受，仅一次占位和一次准备重置。
- 接受与开局、取消、删除／屏蔽并发，以事务提交顺序为准；先加入成功后再删好友不踢人，先删除／屏蔽则加入失败。
- 已加入后重试原幂等请求，仅返回原提交结果，不再次入房。客户端收到旧成功结果仍需查询当前房间，不因回执把已离开的玩家重新加入。
- 过期任务延迟或服务重启不能延长有效期；没有清理任务也必须在读取和操作时拒绝过期记录。

直接分享既有房间链接和邀请码继续可用，游客仍可按原规则加入。这条路径不隐式建立好友关系。

## 9. 页面、通知与多端同步

首页增加好友入口和待处理数量；个人页放资料与设备管理；好友页包含好友、收到／发出的申请、房间邀请和屏蔽管理。准备厅房主可打开好友选择面板，显示哪些好友可邀请与当前发送结果。

通知只包括好友申请和房间邀请。待处理数由未过期 PENDING 数据计算，不设置独立的“已读”状态；打开页面不会自动接受、拒绝或清零。社交通知不遮挡出牌按钮，不暂停／延长对局时钟；对局中可用小徽标提示，不能弹出阻断操作的强制对话框。

同一账号所有有效会话可查看和处理社交数据，但不因此获得麻将控制权。某一端处理后，其他端重新查询并移除旧卡片。退出或身份切换立即清空好友、设备、申请和邀请缓存，旧异步回调不能覆盖新身份。

采用“数据库为准、实时消息提示刷新”的同步方案：

- 持久变更在事务内递增相关用户的 `socialRevision`；提交后向有权会话发送 `social:changed`，只含本人 revision 和变更类别，不含暗手、令牌或其他账号的申请。
- 消息允许合并和重复，不当作持久事实；客户端查询完整社交快照后更新界面。快照含朋友、双方待处理申请、待处理邀请、计数、revision 和 serverTime；限额使数据量有界。
- 连接建立、恢复、页面重新可见时查询快照；页面可见期间每 30 秒补偿查询一次。请求进行中合并刷新，不能为每条消息无限发请求。
- 关系快照取一致数据库视图；在线状态另带进程 `presenceEpoch` 与单调 `presenceSeq`，重启后重建，不能混用旧进程序号。
- 好友资料变化通知仅发给本人及有权读取其当前资料的相关账号；删除／屏蔽后的迟到通知只能触发重新查询，不能重新安装旧关系或状态。
- 私有响应 `Cache-Control: no-store`；离线时明确显示状态可能过时，不能把缓存用于服务端授权。

通知失败不回滚已提交关系；重新查询可以恢复全部当前状态。社交模块失败不阻塞既有麻将裁决、密码登录或历史访问。

## 10. 权限、限流与保存

### 10.1 权限边界

每次操作都重新验证当前会话、正式账号、资源归属及双方关系；不能仅检查 WebSocket 建连时的身份。服务端从会话取操作者，不能信任请求中的 senderUserId。没有权限的申请、邀请、会话统一按 404 或无副作用处理，错误中不包含对方私有数据。

好友关系不授予查看对方战绩、牌谱、私有房间、正在进行的比赛或设备信息的权限。新同桌成员仍不能读取此前比赛；参与者历史权限继续按冻结成员判断。

所有修改沿用 Origin／Cookie 保护、严格 Schema 与 UUID `Idempotency-Key`；同键同载荷重放、同键异载荷返回 `REQUEST_ID_CONFLICT`。幂等记录绑定当前用户、操作、环境和必要的会话范围，不能跨用户重放。设备撤销返回固定成功摘要，不能缓存密码或密码校验结果。

### 10.2 初始限额

以下为计划参数，在实施和验收时配置化；同时保留全站原有基础请求限制。滚动窗口按服务端时间计算，持久保存，重启不清零；拒绝时返回 429 和 retryAfter，不能无限排队。

| 行为 | 限制 |
| --- | --- |
| 资料写入 | 每账号 10 次／小时；实际改名另受 24 小时一次限制 |
| 好友码查找 | 每账号 20 次／分钟、200 次／天；每 IP 100 次／分钟 |
| 新好友申请 | 每账号 10 次／小时、30 次／天；另受账号对冷却和待处理上限限制 |
| 新房间邀请 | 每账号 30 次／小时；同一方向账号对每 60 秒最多一次新邀请 |
| 邀请待处理量 | 每账号收到与发出分别最多 20 条 |
| 申请／邀请状态修改、删除、屏蔽 | 每账号合计 60 次／分钟；不重复计入幂等重放 |
| 设备管理密码校验 | 每账号 5 次失败／15 分钟，每 IP 20 次失败／15 分钟；不得用正确密码无限绕过基础请求限流 |

重复既有申请／邀请和幂等重放不计为新的发送，但仍受基础查询／请求限流。搜索失败与无效操作也受限制，不返回“对方被谁屏蔽”等细节。

### 10.3 保存与运行维护

好友、好友码和屏蔽关系持续保存至主动删除、解除或未来独立账号生命周期规则生效。申请终态和邀请终态保存 30 天后可清理，操作幂等回执至少保留 30 天；回执过期后旧资源 ID 仍不可重新创建关系或入房。

设备撤销和社交安全审计保存 90 天，字段仅含事件、参与账号内部标识、时间、结果与诊断编号，不记录密码、Cookie、验证码、会话 token／hash、完整 User-Agent 或任意文本附言。新存储的设备描述仅保留浏览器／系统大类；过期或撤销会话的新增设备元数据 30 天后清理，不破坏 V3 仍需保留的会话撤销语义。

后台清理分批、有上限、可重入；进行中的房间和比赛不受清理影响。邮件预算不用于社交通知，不增加发信任务。运维需可观察待处理数量、拒绝／限流次数、邀请入房失败原因和同步延迟；玩家侧只展示必要提示。

## 11. 数据与接口工作范围

以下为待实现契约，不表示现有 API 已支持。实施时补充运行时 Schema、完整响应示例、错误码表与测试，若改变本文件语义须先修订文档。

### 11.1 数据

| 数据 | 关键约束 |
| --- | --- |
| 资料扩展 | avatarId、profileVersion、lastNicknameChangedAt；账号身份仍绑定原 userId |
| 好友码 | 环境内唯一且每正式账号一条；和注册同事务创建 |
| 会话元数据 | 专用唯一 sessionId、粗粒度设备类别、lastSeenAt；不把 tokenHash 暴露为 ID |
| friendships | 规范化无序账号对唯一；一条记录表示双向好友，无自好友 |
| friend_requests | 有向发起关系、状态、expiresAt、version；每账号对最多一条 PENDING |
| blocks | blocker／blocked 有向唯一；不允许自己屏蔽自己 |
| room_invitations | 双方、roomId、lobbyGeneration、状态、expiresAt、version；待处理去重 |
| social_user_state | 每账号持久 revision，支持提交后通知与快照重查 |
| 限流、冷却、回执与审计 | 持久化、环境隔离；不能以易失缓存代替并发约束 |

SQLite 与 PostgreSQL 都需支持唯一性、事务、索引及迁移重跑。好友申请接受／屏蔽、邀请接受／开局等操作采用一致锁顺序或现有串行调度，数据库复查不能省略。

邀请接受必须把关系复查、房间写入、准备状态变化、邀请终态、回执和相关 revision 放入同一提交边界。不得先提交社交结果再另行保存房间，也不得先广播未提交状态。服务端内存资料／房间缓存仅在提交成功后更新；提交结果不确定时查询权威记录，不猜测成功或重复执行。

### 11.2 HTTP 草案

统一位于 `/api/v2`，私有查询返回 `{ data, ... }` 的现有约定，失败沿用现有 error 结构；具体包裹层实施时与既有 API 一致，不再创建第二套认证。

| 方法与路径 | 用途与主要输入 |
| --- | --- |
| GET /profile | 本人资料、profileVersion、好友码、可选头像集合 |
| PATCH /profile | displayName、avatarId、expectedProfileVersion |
| GET /auth/sessions | 本人有效会话列表，cursor 分页 |
| POST /auth/sessions/revoke | sessionId、currentPassword、flowId；不接受当前会话 |
| POST /auth/sessions/revoke-others | currentPassword、flowId；保留当前会话 |
| GET /social/snapshot | 完整有界社交快照、revision、serverTime；在线状态独立序号 |
| POST /friends/lookup | friendCode；精确查找，不建立关系 |
| POST /friend-requests | friendCode；申请发送 |
| POST /friend-requests/:requestId/accept | expectedVersion |
| POST /friend-requests/:requestId/reject | expectedVersion |
| POST /friend-requests/:requestId/cancel | expectedVersion |
| DELETE /friends/:friendCode | 删除已有双向好友 |
| GET /blocks | 本人屏蔽列表，每页 20 条 |
| POST /blocks | friendCode；建立屏蔽并清理关系 |
| DELETE /blocks/:friendCode | 解除本人的屏蔽 |
| POST /room-invitations | recipientFriendCode、roomId、lobbyGeneration、expectedRoomVersion |
| POST /room-invitations/:invitationId/accept | expectedVersion；服务器取邀请绑定的房间和轮次 |
| POST /room-invitations/:invitationId/decline | expectedVersion |
| POST /room-invitations/:invitationId/cancel | expectedVersion |

拒绝／撤回／接受均检查版本；已成功的相同幂等请求返回原回执。跨资源失败不返回其他账号的存在性信息。好友查找虽然使用 POST，也执行 Origin 校验与查找限流，不产生申请副作用。

能力接口增加 `profileEditing`、`sessionManagement`、`friends`、`friendInvitations`，以及 socialSchemaVersion 与可公开限额。能力关闭时隐藏入口，服务端同样拒绝新操作；不删除已有数据。

### 11.3 协议与旧客户端

麻将协议 2.0 的选项、回执、streamId／viewSeq 和控制连接语义保持不变。增加头像使用可选字段或版本适配，不要求旧牌谱拥有头像。社交通知单独版本化，不复用麻将动作序号。

仅在旧客户端可忽略新增字段／事件且已有功能不受损时继续使用实时协议 2.0。若实施发现必须破坏原结构，应先更新通信协议、兼容策略与发布说明，不静默复用旧版本。旧前端可以继续玩既有游戏，不能显示假好友入口。
